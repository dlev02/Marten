# Credit-score integration research

Reviewed September 10, 2026 for Marten's personal/family use. The constraint was no new spending, vendor contracts, or account creation. This review did not identify a verified free, self-service official API that supplies live personal credit scores under those constraints. Free consumer score access is different from developer API access.

## Practical free approach

Free import is feasible even without a direct credit-score API. Marten could read a user-supplied score screenshot or PDF, then require confirmation of the extracted fields. Manual entry remains a fallback. This reduces transcription work without asking Marten to retain credit-service login credentials.

Verified free consumer sources include:

- [Experian](https://www.experian.com/credit/credit-score/): FICO Score 8 with daily updates available through its consumer service.
- [TransUnion Credit Essentials](https://www.transunion.com/free-credit-score): VantageScore 3.0 with free daily score/report refreshes through its consumer membership.

TransUnion's explanation also confirms that the free weekly reports from AnnualCreditReport.com do not include a credit score. Importing a credit report alone therefore does not guarantee a score to display. Plaid liabilities, a credit report, and a credit score are separate data products.

Every stored observation should retain **score, bureau, scoring model/version, as-of date, and source**. Keep histories for different models/bureaus separate: a FICO Score 8 and a VantageScore 3.0 are not interchangeable measurements. Imported content should be confirmed by the user, and source files need not be retained after extraction.

### Assisted capture versus scheduled synchronization

A technically feasible companion workflow is: the user opens an existing score page, explicitly invokes capture, reviews the extracted score/bureau/model/date, and saves it to Marten. A desktop assistant or browser extension with explicit access could read that displayed information. A normal Marten webpage cannot inspect another site's signed-in tab because of browser origin isolation. An uploaded screenshot/PDF avoids that cross-site integration requirement.

This review did not verify provider permission or an official interface for unattended portal scraping. A companion should use only the explicitly selected page/document, leave login/MFA with the user, and avoid collecting cookies, passwords, unrelated report data, or calling hidden provider endpoints. It should not trigger a score refresh or new report request as part of merely importing an already displayed observation. Site terms and available browser-tool permissions still need to support the selected implementation.

A periodic helper could remind the user to capture a new observation and assist while their selected page is open. It should report stale data when authentication or page changes prevent capture, and should not be advertised as guaranteed background synchronization. No complete historical score export was verified for Credit Karma in this review; do not promise an archive migration without inspecting the actual user-provided export.

[Plaid Statements](https://plaid.com/docs/statements/) can retrieve institution-branded statement PDFs for supported accounts and requires Statements-specific setup/consent. Trial includes that product, but institution coverage and the presence of a score in a particular PDF remain separate checks. This is a possible later document-ingestion route, not a verified credit-score feed or proof that Marten's existing Items can retrieve those statements today.

No provider account, contract, or paid service was created during this research.

## Implemented local history — September 11, 2026

`/credit-scores` records reviewed score, as-of date, bureau, model/version, source and manual/PDF entry method. The authenticated backend validates whole-number scores from 300 to 850 and a real, nonfuture date. Each bureau/model pair has its own history and point change; one pair cannot have duplicate observations on the same date. Users can edit or delete their own observations. Reads and writes derive ownership from the session. The history is bounded to 1,000 observations per user and is included in sample-workspace cleanup.

Supported models are base FICO Scores 8, 9, 10 and 10T and VantageScore 3.0 and 4.0. FICO's [model-version guide](https://www.myfico.com/credit-education/credit-scores/fico-score-versions) distinguishes the 300–850 base scale from 250–900 Auto/Bankcard variants; those specialized variants are explicitly outside this screen's scope. VantageScore's [implementation guide](https://www.vantagescore.com/why-vantagescore/how-to-implement) confirms the 300–850 range for 3.0 and 4.0. No scores are averaged across models or converted into another score type.

PDF import uses maintained Mozilla [PDF.js 6.3.289](https://github.com/mozilla/pdf.js/releases/tag/v6.3.289), verified against the official release and npm package on September 11. The [browser API](https://mozilla.github.io/pdf.js/examples/) reads bytes and page text. The library and matching bundled worker load only when Import PDF is used. Files are limited to 10 MB, 20 pages, 100,000 text characters and a 20-second reading deadline; the document task is destroyed afterward. No PDF bytes, filename, complete text, storage object or account credentials are sent to Convex. Only the values the user confirms in the review form are saved.

Extraction is intentionally narrow: one explicit FICO/credit-score/VantageScore label directly associated with a plausible score. Amounts and scale endpoints are ignored. Multiple possible scores, no readable text, encrypted documents and malformed/oversized files lead to manual entry. Bureau, supported model and as-of date are suggested only when the nearby text identifies one value; issuer names and statement closing dates do not supply missing score metadata. The review form always opens before a save. This is neither OCR nor an automatic score feed and is not a general archive importer for multi-score reports.

Nine focused tests passed: authenticated CRUD/owner isolation; score/date/source bounds and duplicate-date rejection; bureau/model history separation; explicit and ambiguous text extraction; and actual PDF.js reading of fictional text, no-text, password-protected and 21-page fixture files. Type checking, affected-file ESLint and the production build passed. The development backend accepted the feature at 00:58:29 America/Chicago.

Rendered verification used fictional QA data. Importing the text fixture opened a review with 742, September 1, TransUnion, FICO Score 8 and its explicit source; the observation was saved only after confirmation. A manually entered 750 on September 10 produced a +8 change within the same history and persisted after reload. Editing its bureau to Equifax created a separate one-observation series without an invented change; deleting that edited observation through confirmation retained the original TransUnion score. Importing the password-protected fixture opened manual review with all fields empty and a clear explanation.

Desktop light/dark history and the edit form were inspected. Tablet at 820 px and phone at 390 px were also inspected, including the calendar and history. The phone history initially overflowed because its visually hidden table header escaped the scroll container; making that container positioned fixed the page width to 390 px. Screenshots are in `output/playwright/marten-credit-{tablet-light,phone-dark,phone-date-dark,phone-history-dark}.png`. PDF reading remains text-only and user-initiated; real provider documents, OCR and a live score feed were not exercised or enabled.
