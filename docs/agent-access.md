# AI connections

Marten exposes its existing finance features to an assistant the user already has. It does not run a model or require a model API key. Settings → AI connections controls two separate connections:

- **Browser agent access** registers WebMCP tools in a supporting browser while the personal workspace is open. Access and edits start off. The normal browser interface remains available when WebMCP is unavailable.
- **Remote MCP** uses OAuth consent and the Convex HTTP endpoint shown in Settings. Each assistant receives its own revocable grant. A browser tab does not need to stay open after linking, so scheduled tasks and automations can run unattended.
- **Access keys** (Settings → AI connections → Access keys) are for assistants that call an API with a saved key instead of signing in, such as Meta Muse custom connectors. A key is a grant with its own credential type and reaches the same `/mcp` endpoint.

Both use the schemas in [`agentTools.ts`](../convex/lib/agentTools.ts) and the same authenticated operations. Signed-out users, anonymous demo accounts, and sample workspaces cannot enable either connection. Existing account IDs never authorize access to another user's records.

## Available tools

| Feature               | Reads                                                                                                           | Edits requiring separate consent                                                                                                               |
| --------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts              | Balances, currencies, cached update times, statements, computed `netWorthCents` with the app's rule             | Name, hidden state, net-worth inclusion; add a manual account (`create_account`); relay balances and statement details (`record_account_snapshot`) and backfill manual balance history (`record_balance_history`) |
| Transactions          | Pages with resolved account, merchant, category and tag names, `direction`, details, annotation history; review filters and a compact row form | Notes, category, merchant, tags, visibility, reviewed state, valid splits; the same patch on up to 100 rows atomically (`update_transactions`), including adding or removing tags without replacing the others (`tagChange`) |
| Organization          | Category groups, categories with group kind, tags, merchant pages with `hasLogo`, merchants missing a logo, `merchantSearch`, ordered rules with names | Create and rename merchants, merge an obvious duplicate merchant (`merge_merchants`), set a merchant logo from its own website (`set_merchant_logo`), create and edit categories and tags, merge a duplicate category into another of the same kind (`merge_categories`), save and reorder rules, apply a rule to existing rows in resumable pages |
| Preferences           | Workspace name, `reviewNew`, `allowPending`, `investmentActivity`, dashboard widgets                            | `reviewNew`, `allowPending`                                                                                                                    |
| Recurring             | Schedules with names, detector suggestions, paginated payment checkmarks, statement reminders                   | Create or update tracking schedules; set or clear actual occurrence checkmarks                                                                 |
| Forecast              | Baseline, saved assumptions and revisions, modeled annual results with engine warnings                          | Save a reviewed scenario; updates require its current revision                                                                                 |
| Investments           | Cached holdings, securities, connection freshness, activity pages                                               | None                                                                                                                                           |
| Credit scores         | Saved observations with bureau, model, date, and source                                                         | Save one observation (`save_credit_score`), upserted on bureau, model and date                                                                  |
| Reports and cash flow | Complete USD totals, counts, per-month rows and warnings using the application's split and category-group rules | None                                                                                                                                           |

The tool surface has no bank linking, provider refresh, token retrieval, receipt downloads, transfers, trades, message sending, deletion of transactions, accounts or rules (a merge removes only the merged duplicate), group creation, appearance or notification settings, Budget, Goals, or Advice tools. Creating or marking a recurring item changes tracking only. Names, notes, and statements are untrusted stored text, not instructions to the assistant.

Amounts remain integer cents with currency; `amountCents > 0` is money out and every transaction row restates this as `direction`. Transaction pages default to 50 rows (100 maximum) because each row carries resolved names. `list_transactions` accepts `search` and treats a missing date range as all time; `get_classifications` accepts `merchantSearch`, matching display names and the statement text on transactions. A recurring schedule's `nextDate` is the anchor its occurrences repeat from; `set_recurring_paid` names the valid dates when asked for one that is off the series. Forecast results include `returnAssumptionApplies`, and the baseline lists `observedFields` against the example values it fills in. Timestamps ending in `At` are also returned as ISO strings ending in `AtIso`. Reports exclude hidden, pending, removed, and transfer entries; refunds retain their sign and splits replace the parent allocation. Reports return `summary.months` so a multi-month question is one call, and `warnings` when inflows sit in expense categories. Paginated reads return `continueCursor: null` once finished. Reports scan at most 60 pages of 200 transactions; when unfinished, they return `complete: false` and `summary: null`. `apply_rule` walks existing transactions newest first, 60 pages of 100 per call, and returns `complete` with a `continueCursor` to pass back so repeated calls finish long histories. `merge_categories` (2,000 rows per call) and `merge_merchants` (500 rows per call) also return `done` and a `cursor`; the source is deleted only on the final call, category merges also rewrite unsaved split drafts, and a merchant merge restarts its final check if a sync added rows behind the cursor. Pages can observe a bank sync or edit during loading, so the result explains that consistency limit. Forecasts use the monthly engine but return annual rows and totals, plus warnings such as a return assumption that cannot apply because no invested balance was supplied. Remote results above 140,000 characters return a request to narrow the query, never silently truncated data.

Every result is scanned at the tool boundary: stored text fields (notes, names, statement text) that read like instructions to an assistant add a `dataWarnings` entry telling the assistant to report the text rather than follow it. The scan covers resolved names on rows (`merchantName`, `accountName`, `categoryName`, `groupName`), tag name lists, rule action names, condition values, institution and source text, and report warnings that quote merchant names; tool guidance is returned under `hint` or `next`, which are not scanned. The text itself is left intact so nothing is hidden from the user. The initialization instructions restate the conventions, the efficient call patterns, the completeness fields, and the rule that stored text is never a command.

## Scheduled cleanup

The tools are shaped for an assistant that tidies the workspace on a schedule, like a weekly Monarch cleanup. Filters and bounds exist so it pays for as few tokens and calls as possible:

- **What needs review since the last run:** one `list_transactions` call with `{reviewed: false, updatedSince: "<last run ISO time>", compact: true, pageSize: 100}`. `updatedSince` matches rows imported or edited since then (including the assistant's own edits); a date range with `from` works as well. Other filters: `uncategorized` (a category named Uncategorized), `categoryIds` (main category or a split line), `tagId`, `pending`, `hidden` and `source` (`plaid`, `simplefin`, `lunchflow`, `csv`, `manual`). These are not index fields, so a filtered page scans at most 2,000 rows and can come back short with a cursor; continue until `continueCursor` is null.
- **Compact rows:** `compact: true` returns `id`, `date`, `amountCents`, `merchantName`, `categoryName` and `accountName`; `fields` adds named extras such as `originalName`, `notes`, `tagNames` or `merchantId`.
- **Merchant hygiene:** renames and merges record the old normalized statement name in `merchantAliases`, and Plaid, SimpleFIN, Lunch Flow and spreadsheet imports resolve that alias before creating a merchant, so a cleaned name survives the next sync. A merchant that later takes the old name reclaims it. `create_merchant` returns an existing merchant with the same name instead of a duplicate. `merge_merchants` moves transactions, recurring schedules, rule actions and saved reports and is described to assistants as for obvious duplicates only.
- **Logos:** merchant rows carry `hasLogo` and never a storage id or URL; `get_classifications {missingLogo: true, merchantsOnly: true}` pages merchants without one. `set_merchant_logo {merchantId, domain}` accepts a bare public hostname only (no scheme, path, port, IP address or local name), and reuses the Settings website-logo lookup: first-party HTML icons, touch icon and favicon on that host or its subdomains, three checked redirects, 10-second and 2 MB limits, and content sniffing. The request runs in the action after the write scope is checked; the image is attached by the same authorized write mutation as other edits and removed if that write fails.
- **Limits in schemas:** tool schemas import the server's limits (30 tags and 10,000 note characters per transaction, 50 split lines, rule bounds), and an invalid input names the field and limit, for example `patch.tagIds allows at most 30 items`.
- **Rules:** `reorder_rules` takes every rule id exactly once. There is no rule deletion tool; an assistant pauses a rule with `save_rule` and `enabled: false`.

A ready-made routine is in [docs/skills](skills/README.md): the [marten-cleanup skill](skills/marten-cleanup/SKILL.md) and how to schedule it in Claude, ChatGPT, Grok and Muse.

## Snapshots from an assistant's own finance data

Assistants reliably relay single, checkable numbers they can already see (a balance, a statement due date, a monthly credit score) but not whole transaction feeds, so transaction sync is deliberately not offered. Four edit tools cover the numbers; each is an upsert, so a scheduled task can run twice without creating anything twice.

- `create_account` adds a **manual** account (USD, last four digits only, subtype from the Add account form's list for the kind, opening balance dated `balanceDate`). An account with the same institution, kind and mask (or name when there is no mask) is returned as `existing` instead, including a bank-connected one, which is never duplicated.
- `record_account_snapshot` takes up to 50 accounts: `balanceCents` (with optional `availableCents`, `limitCents`) as of `asOf`, and for credit and loan accounts `statementCents`, `statementDate`, `dueDate`, `minimumCents`. Each account and date keeps one `balances` row; a rerun reports `unchanged`. Only the newest dated balance becomes the current balance. Dates may be at most one day ahead (time zones); a due date must be within about a year. Each account gets `updated`, `unchanged` or `refused` with reasons, plus `refusedFields` and `warnings` (for example a negative balance on a card, which Marten reads as a credit balance).
  - Manual accounts accept every field. A new due date starts a new statement, so amounts it omits are cleared rather than carried over.
  - Bank-connected accounts (Plaid, SimpleFIN, Lunch Flow) keep their feed: balances are refused, and statement fields are accepted only when the feed supplies no statement. They are stored as the account's **statement reminder**, which bank syncs never clear and which Recurring, the dashboard and payment reminders already prefer. `statementDate` has no place there and is refused.
  - A due date or statement date older than the one Marten has is refused as stale.
- `record_balance_history` saves up to 100 dated balances for one manual account through the same import path as the Balance history dialog; dates are unique per call and never in the future.
- `save_credit_score` upserts on bureau, model and date with entry method `agent`; its source defaults to the connection name. A score the user entered or reviewed from a PDF is never replaced by a different relayed one (`refused`), and saving an assistant's score from the form makes it the user's (`manual`).

**Provenance.** Accounts, balance rows, statement reminders and credit scores written by an assistant record `writtenBy` (the grant id, the connection's display name at the time, and when). The interface says so calmly: the account row reads "Updated by ChatGPT · 2h ago", the account detail explains it in an info tip, statement cards on Recurring read "Added by ChatGPT", and the credit-score history's Entry column reads "Added by ChatGPT". An owner's own edit to those values clears `writtenBy`.

MCP annotations: `merge_merchants` and `merge_categories` are `destructiveHint: true`; `create_merchant`, `create_account` and the other create tools are not idempotent; the `record_*` tools and `save_credit_score` are idempotent upserts.

## Deployment configuration

The endpoint is `${CONVEX_SITE_URL}/mcp`, using the deployment's **`.convex.site` HTTP origin**, not its `.convex.cloud` client origin. Set `AGENT_APP_ORIGIN` on that same Convex deployment to the exact frontend origin that serves `/agent-authorize`. It falls back to `SITE_URL`. A publicly reachable HTTPS frontend is needed for hosted/mobile connection flows; an HTTP loopback origin is accepted for local development and shown as not remotely ready. Configure the frontend host's SPA fallback so a direct visit to `/agent-authorize` loads the app and preserves the request parameter through sign-in.

The backend uses the maintained `@modelcontextprotocol/server` SDK and Convex rate-limiter component. Deploy the Convex configuration, schema, HTTP routes, functions, and generated bindings together. `npx convex dev --once` writes to the selected development deployment; production publication is a separate authorized release step.

Public discovery endpoints are:

- `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-protected-resource`
- `/.well-known/oauth-authorization-server/agent` for the `${CONVEX_SITE_URL}/agent` issuer; root and issuer-relative discovery aliases are also served. It advertises `registration_endpoint`, `offline_access`, and both grant types.

An unauthenticated `/mcp` request returns HTTP 401 with a `WWW-Authenticate` discovery pointer whose `scope` names every supported scope (`finance:read finance:write offline_access`), so spec-following clients ask for editing and refresh up front. That does not grant editing: the consent screen still starts at read-only. OAuth authorization, token exchange, revocation, and dynamic client registration (`/agent/oauth/register`) are under `/agent/oauth/`. Token requests use `application/x-www-form-urlencoded`, never query-string tokens or a model API key.

## Connecting ChatGPT or Claude

Copy the MCP URL from Marten Settings into the assistant's custom MCP connection settings, choose OAuth, sign in to Marten, and review the requested access. Start with read access; grant editing only when desired. Under **Keep access**, choose **While it's in use** (the default, suited to scheduled tasks), **For 30 days**, or **Until I disconnect it**. Availability depends on the assistant's plan, workspace policy, and client. Use the current [ChatGPT connection guide](https://developers.openai.com/plugins/deploy/connect-chatgpt) or [Claude custom connector guide](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) for the host's exact controls.

Client ID Metadata Documents (CIMD) are preferred. The server advertises public-client authentication (`none`) and validates metadata from the approved ChatGPT/Claude origins. It supports ChatGPT's plural authentication-method field even when its legacy singular preference is `private_key_jwt`; the advertised intersection selects `none`. The live [ChatGPT metadata document](https://chatgpt.com/oauth/client.json) and [OpenAI OAuth contract](https://developers.openai.com/plugins/build/auth) were checked on September 11, 2026.

If a client asks for a predefined client ID, these are available with no client secret:

| Client ID        | Registered callback                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------- |
| `marten-chatgpt` | `https://chatgpt.com/connector_platform_oauth_redirect`                                   |
| `marten-claude`  | `https://claude.ai/api/mcp/auth_callback`                                                 |
| `marten-local`   | HTTP `localhost` or `127.0.0.1`, `/callback` or `/oauth/callback`, with an ephemeral port |

ChatGPT's stable callback requires the exact issuer in every OAuth success/error redirect; Marten supplies it. CIMD also supports ChatGPT's callback-specific metadata documents. Claude Code declares loopback callbacks, while Claude's hosted clients use the hosted callback above. A callback must match its registered host and path; only the port of an explicitly registered loopback callback may vary. See [Claude's authentication reference](https://claude.com/docs/connectors/building/authentication).

## Connecting Grok and other self-registering assistants

Assistants without a predefined Marten client ID register themselves through [RFC 7591 dynamic client registration](https://www.rfc-editor.org/rfc/rfc7591). Paste the MCP URL into the assistant's connector settings and choose OAuth; the assistant registers, then sends you to Marten's approval screen. Registration accepts only public clients (`token_endpoint_auth_method` `none`, S256 PKCE), `authorization_code` and `refresh_token`, and one to five callbacks that are HTTPS or loopback HTTP (`127.0.0.1`, `localhost`, `[::1]`) without credentials or fragments. Only the client ID, a cleaned display name (60 characters, control and direction-override characters removed) and the callbacks are stored. Registration is limited to five per hour per caller address (hashed) and 500 new registrations per day overall; a daily sweep removes registrations more than a day old with no live connection.

Registered clients, like any client not on the ChatGPT/Claude allowlist, appear on the approval screen as **Unverified app** with the callback host shown prominently, and with the same badge in Settings. Grok's connector flow has not been tested against a live Grok account; the automated tests use a fictional registration.

Client metadata documents from hosts other than ChatGPT and Claude are still refused. The Convex runtime cannot inspect the address a hostname resolves to, so an arbitrary-host fetch could not be protected against private-network targets; dynamic registration covers those clients without Marten fetching anything.

## Connecting with an access key (Meta Muse)

Muse's custom connectors call an API with a stored key rather than signing in. In Settings → AI connections → Access keys, choose **Create key**, name it, choose **Read only** or **Read and edit**, and choose 30 days, 90 days, 1 year or **Until I revoke it**. Copy the key when it appears; it is shown once. In the connector, use the MCP URL as the server and send `Authorization: Bearer <key>`. Keys begin with `mrtn_` so secret scanners can recognise them. Only a SHA-256 hash is stored. A key gets the same scope checks, 403 scope challenge, per-connection rate limit, activity record and last-used time as an OAuth grant, counts toward the 50-connection limit, and stops working immediately when revoked. It cannot be used at the token or revocation endpoints. Whether a particular Muse connector build speaks MCP over Streamable HTTP has not been verified against a live Muse account.

## Scopes

Read-only grants receive `finance:read`; edits require `finance:write`. Insufficient edit scope returns HTTP 403 with an OAuth scope challenge. Reconnect and approve editing if the assistant requests that additional capability.

## Authorization and operational checks

OAuth uses S256 PKCE, single-use codes, exact client/callback/resource binding, one-hour access tokens, and rotating refresh tokens. `offline_access` is accepted and advertised; refresh tokens are issued whether or not it is requested. A grant's lifetime is chosen at consent: **while in use** grants end after 90 days without a refresh or tool call (each refresh moves the deadline, and tool calls move it at most hourly), **30-day** grants end on a fixed date, and **until disconnected** grants have no deadline. Grants created before September 29, 2026 keep their original 30-day end date; reconnect them to choose a new lifetime. A refresh token presented again within two minutes of its first use (a hosted client retrying after a lost response) receives a fresh pair from the same grant, at most three times; presenting it later is treated as replay and revokes the grant. Code replay revokes its grant. A refresh request with a narrower `scope` narrows only the access token it issues (RFC 6749 §6); the grant and its refresh token keep the consented scopes, and asking for `offline_access` is never treated as escalation. Revoking a grant deletes its tokens. An hourly sweep removes expired token rows; used refresh tokens are kept one day for replay detection. An account with a pending deletion request cannot use, refresh, create, or approve any connection or key. Only cryptographic hashes are stored for request secrets, codes, and tokens. Request/token cleanup is scheduled after expiry. Revocation and eligibility are checked on every operation, including a final check after a multi-page report. Turning off browser access does not revoke remote grants; disconnect those individually in Settings.

Provider identifiers, credential fields, storage IDs, and asset/download URLs are removed at the tool-output boundary. The agent activity list stores tool name, source, the connection's display name, time and success. For each edit it also stores a one-line summary ("Recategorized 12 transactions", "Updated 3 accounts (1 refused)"), counts, and up to 25 before/after values of changed fields (ids, names, flags, dates and amounts; text cut to 80 characters; never arguments as sent, credentials, storage ids or conversation text). Settings shows the summary line; the before/after values stay on the server. Transaction history rows made by an assistant carry the connection's name ("Changed category and review status · by ChatGPT"), including rows changed by `apply_rule`. A daily job deletes activity older than 90 days in batches of 500. A grant's last-used time (shown in Settings with its expiry) is refreshed at most once an hour so parallel calls from one assistant do not contend on the grant record. Data already sent to an assistant remains subject to that service's own settings.

HTTP validates allowed origins and bounds request bodies. OAuth start/token endpoints and tool execution are rate limited. Invalid client metadata cannot cause arbitrary-host fetches: discovery accepts only the approved HTTPS origins, refuses redirects, validates returned client identity and callback origins, and limits response time and size.

[`agentAccess.test.ts`](../convex/agentAccess.test.ts) covers consent, ownership, atomic edit validation, report completeness, model separation, OAuth discovery/PKCE/token lifecycle, secret redaction, and actual SDK requests for both `2025-11-25` and `2026-07-28`. The latter uses the current [Streamable HTTP per-request envelope](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Tests use fictional data and mocked client metadata; passing them does not establish a successful link inside a real ChatGPT or Claude account. Verify discovery, sign-in return, a read, a consented reversible edit, and disconnect in each intended client before claiming that client works end to end.
